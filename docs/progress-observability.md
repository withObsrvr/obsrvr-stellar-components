# Live ingest progress (incremental)

The live pipeline is `raw-ledger-source -> stellar-ledger-processor -> ducklake-sink -> quack-ducklake-server`. These process-local gauges have **no ledger labels** (bounded cardinality). Compare them across components using the deployment's pipeline/run/component identity in the scrape target labels and logs; do not label metrics with a ledger number or an unbounded run ID. Flow events carry their source component ID and the processor copies input metadata to its output event, including any upstream correlation IDs. The ingest RPC currently does **not** carry those IDs, so a server-side gauge cannot be attributed to a run when multiple runs share a server.

- Processor: `obsrvr_stellar_processor_last_received_ledger` (successfully decoded XDR entering the callback), `obsrvr_stellar_processor_last_transformed_ledger` (successful normalization), and `obsrvr_stellar_processor_transform_errors_total`. Set `PROCESSOR_METRICS_ADDR=:8091` to expose `/metrics` separately from the flowctl SDK's health port. Malformed protobuf/XDR rejected by the SDK **before** the callback is not counted here.
- Sink in `ingest-rpc` mode: `obsrvr_ducklake_sink_last_sent_ledger` (stream Send succeeded), `obsrvr_ducklake_sink_last_acknowledged_ledger` and `obsrvr_ducklake_sink_last_acknowledged_timestamp_seconds` (matching ack received). No local sink gauge is a durability claim. Existing `/healthz` reports write errors and `/metrics` reports retries.
- Server: `obsrvr_ducklake_ingest_last_received_ledger` (live batch admitted), `obsrvr_ducklake_ingest_last_committed_ledger` (commit succeeded, initialized from `max(ledger_sequence)` in `ingest_watermarks` at startup), `obsrvr_ducklake_ingest_last_commit_timestamp_seconds` (successful commit in this process; zero after restart). The existing `obsrvr_ducklake_ingest_last_ledger` is an **ack** gauge, not a commit gauge. Backfill range commits update committed progress but not live received progress. `/metrics` is on `QUACK_HEALTH_ADDR`.

A nonzero receive-minus-commit gap after retries suggests server/storage failure; a sink sent-minus-ack gap suggests transport or server failure. Gauges are process-local and may reset on restart or move backwards during replay: never use them as a checkpoint. Verify the durable boundary with the `ingest_watermarks` min/max/gap query in `components/ducklake-sink/README.md`. Commit age is meaningful only when the timestamp is nonzero and work is expected; use source tip and pipeline state to distinguish an idle pipeline from a stall.

The sink and server also serve `/live` (process HTTP responsiveness), `/ready` (server dependency/checkpoint health or sink last-write health plus a bounded TCP check of the ingest endpoint in ingest-rpc mode; not authentication or commit proof), `/health` (same current diagnostic response), and legacy `/healthz`. Liveness intentionally does not query DuckLake. These paths do not replace durable catalog proof. Invalid/empty ledger batches and cursor mismatches are rejected before sink writes; cancellation while waiting for sink admission or between retries is returned separately from write failure. Until the error-aware SDK is released, non-cancellation sink errors still terminate the process rather than risk a false acknowledgement.

The local `deploy/monitoring/quack-ducklake-alerts.yml` adds receive/commit divergence and pending-work commit-age rules scoped to the primary server. They need a real scrape/alert evaluation in the target environment before enabling paging. No pipeline-tip lag alert is possible here until the source exports an authoritative tip metric and labels identifying the same pipeline.

**Still open:** SDK/runtime error propagation and raw decode failure reporting, correlation IDs through ingest RPC, terminal error classification, standardized `/live`/`/ready`/`/health`, alert/dashboard deployment, source-failure E2E and live-tip gate. Do not change SDK or source dependency versions until their tagged releases are available.
